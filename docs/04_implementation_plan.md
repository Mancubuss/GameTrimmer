# GameTrimmer — План втілення та стек технологій

*Дата: 2026-07-12. Базується на: concept_mvp.txt, 01_specification.md, user stories, патерни tikione-steam-cleaner.*
*Рішення: перехід з C++/Qt на **Rust + egui** — попередній стек давав неадекватний розмір збірки (40–70 МБ) відносно функціональності.*

## 1. Контекст

Попередній прототип (C++20 + Qt 6.8 + SQLite, `src/`) реалізував парсер `libraryfolders.vdf`, обгортку SQLite та каркас аналізатора. Логіка переноситься в Rust; втрати мінімальні, бо основна складність проєкту (движок визначення локалізацій) ще не була реалізована. C++-код лишається в історії git як довідник поведінки.

## 2. Стек технологій

| Компонент | Вибір | Примітка |
|---|---|---|
| Мова | Rust (stable, MSVC toolchain) | один статичний exe ~5–10 МБ |
| GUI | `eframe`/`egui` + `egui_extras` (таблиці) | темна тема за промовчанням, High-DPI з коробки |
| БД | `rusqlite` з feature `bundled` | SQLite статично в бінарнику, без DLL |
| Сканування ФС | `walkdir` + `rayon` | паралельний обхід дисків |
| Regex | `regex` (+ `RegexSet` для пакетного матчингу) | case-insensitive `(?i)`, дуже швидкий |
| Правила | `serde` + `serde_json` → зовнішній `rules.json` | оновлення патернів без перекомпіляції |
| Steam VDF/ACF | `keyvalues-parser` (або власний мінімальний парсер) | `libraryfolders.vdf`, `appmanifest_*.acf` |
| Реєстр Windows | `winreg` | Steam, GOG, Ubisoft, EA |
| Видалення в Кошик | `trash` | безпечне видалення за промовчанням |
| Тести | вбудований `cargo test` | корпусні тести движка мов |
| Лінт/формат | `clippy`, `rustfmt` | стандартний інструментарій |

### Профіль релізу (розмір бінарника)

```toml
[profile.release]
opt-level = "z"       # або 3, якщо швидкість сканування важливіша
lto = "fat"
codegen-units = 1
strip = true
panic = "abort"
```

Очікуваний результат: 5–10 МБ, один exe, поруч — лише `rules.json` та база `gametrimmer.db` (створюється при першому запуску).

## 3. Архітектура (cargo workspace)

```
gametrimmer/
├── Cargo.toml            (workspace)
├── crates/
│   ├── core/             — уся логіка, без GUI; покривається тестами
│   │   ├── providers/    — виявлення бібліотек: Steam, Epic, GOG, EA, Ubisoft + ручні теки
│   │   ├── scanner/      — walkdir+rayon обхід, індексація в SQLite
│   │   ├── rules/        — regex-правила категорій (redist/docs/bonus) з rules.json
│   │   ├── langdetect/   — движок визначення локалізацій (§5)
│   │   ├── ops/          — Кошик/карантин, журнал операцій, відновлення
│   │   └── db/           — rusqlite: схема, міграції, пакетні транзакції
│   └── app/              — eframe: дерево знахідок, чекбокси, прогрес, налаштування
├── rules.json            — зовнішній файл патернів
└── tests/corpus/         — корпус шляхів для тестів мовного движка
```

`core` не залежить від egui — це дає швидкі headless-тести та можливість CLI-режиму в майбутньому.

**Потоки:** сканування й аналіз — у фонових потоках (`std::thread` + `crossbeam-channel`); UI отримує прогрес через канал і будить перерисовку `egui::Context::request_repaint()`. Скасування — через `AtomicBool`.

### Схема БД

- `game_libraries(id, vendor, path)`;
- `games(id, library_id, name, install_dir, app_id)` — з маніфестів лаунчерів;
- `files(id, game_id, rel_path, size, mtime)`;
- `findings(file_id, category, rule_id, confidence, lang_tag)`;
- `operations(id, ts, action, src_path, dst_path, status)` — журнал для відновлення.

Вставки — пакетами по кілька тисяч у транзакції (prepared statements).

## 4. Провайдери бібліотек (мультивендорність)

| Вендор | Джерело даних |
|---|---|
| Steam | реєстр → `libraryfolders.vdf` + `appmanifest_*.acf` (назви ігор, теки `steamapps/common/*`) |
| Epic | `C:\ProgramData\Epic\EpicGamesLauncher\Data\Manifests\*.item` (JSON → serde) |
| GOG Galaxy | реєстр `HKLM\SOFTWARE\WOW6432Node\GOG.com\Games` або `galaxy-2.0.db` (SQLite) |
| Ubisoft Connect | реєстр `HKLM\SOFTWARE\WOW6432Node\Ubisoft\Launcher\Installs` |
| EA App | реєстр + `__Installer/installerdata.xml` у теці гри |
| Будь-що інше | ручне додавання теки як «бібліотеки» |

Xbox/MS Store свідомо пропускаємо: теки `WindowsApps` захищені ACL, втручання шкідливе.

Спільний трейт:

```rust
trait LibraryProvider {
    fn name(&self) -> &str;
    fn discover(&self) -> Result<Vec<GameInstall>, ProviderError>;
}
```

Нові вендори додаються без змін решти коду.

## 5. Движок визначення локалізацій (ключовий ризик проєкту)

Досвід попередніх спроб (прямий матчинг ISO 639/15924/3166/IETF без регістру) дає масові хибні спрацювання: двобуквені коди — це звичайні слова та склади (`it`, `no`, `de`, `pl`, `es`). Дизайн — **токенізація + словник із рівнями довіри + контекстний скоринг**.

### 5.1. Токенізація

Шлях розбивається на сегменти (теки, ім'я файлу, розширення), сегменти — на токени за роздільниками `_ - . ( ) [ ] пробіл` та межами CamelCase (`SpanishNation` → `Spanish`, `Nation`).

### 5.2. Словник мовних ідентифікаторів — три рівні довіри

- **Рівень A (самодостатні, висока довіра):**
  - повні назви мов англійською та рідною: `spanish`, `german`, `french`, `italiano`, `deutsch`, `francais`, `polski`, `russian`, `japanese`…;
  - локальні теги з регіоном: `en-US`, `es_ES`, `pt-BR`, `zh-CN`, `Spanish(Spain)` — патерн `[a-z]{2,3}[-_(][a-z]{2}\)?`;
- **Рівень B (потребують контексту):** трибуквені коди ISO 639-2/3 (`spa`, `deu`, `fra`, `pol`) — лише якщо токен стоїть окремо (`_spa.`, `\spa\`) **і** поряд є мовний контекст (5.3);
- **Рівень C (лише в мовному наборі):** двобуквені коди ISO 639-1 (`es`, `de`, `it`, `pl`) — **ніколи** не спрацьовують самі по собі; тільки як елемент «мовної сім'ї» (5.4).

Словник генерується один раз зі CLDR/ISO-таблиць у статичну структуру (build-скрипт або закомічений `langs.rs` / `langs.json`).

### 5.3. Контекстний скоринг сегментів шляху

- **Позитивні маркери локалізації** (підвищують упевненість): `sound`, `soundbanks`, `voice`, `vo`, `audio`, `speech`, `dub`, `subtitles`, `caption`, `text`, `strings`, `loc`, `localization`, `localized`, `lang`, `language`, `l10n`, `movies` + мовний токен у назві файлу.
- **Негативні маркери ігрового вмісту** (блокують): `art`, `units`, `models`, `textures`, `structures`, `buildings`, `history`, `decisions`, `events`, `missions`, `maps`, `scripts`, `music`.

Приклади з ТЗ проходять коректно:
- `...\sound\soundbanks\hhpc\Spanish(Spain)_patch_1.snd` → A-токен + маркер `soundbanks` → **локалізація (озвучка)**;
- `...\resource\closecaption_spanish.dat` → A-токен + маркер `caption` → **локалізація (субтитри)**;
- `...\Art\Units\King Spanish\` → A-токен, але негативний маркер `Art`/`Units` → **ігровий ресурс, не чіпати**;
- `...\decisions\SpanishNation.txt` → негативний маркер `decisions` → **не чіпати**.

### 5.4. Евристика «мовної сім'ї» (найсильніший сигнал)

Якщо в одній теці лежать сусідні файли/підтеки, що відрізняються лише мовним токеном (`Spanish(Spain)_patch_1.snd`, `French(France)_patch_1.snd`, `German_patch_1.snd`…) — це набір локалізацій з майже 100% упевненістю, навіть без контекстних маркерів. Ця евристика легалізує і рівень C: теки `en/ de/ fr/ es/ pl/` поряд — очевидний мовний набір.

### 5.5. Правила безпеки

- Keep-list: `uk`, `ukr`, `ukrainian`, `en`, `eng`, `english` + усі регіональні варіанти (`en-US`, `en-GB`) — ніколи не пропонуються до видалення (налаштовується в UI);
- файл без мовного токена не є кандидатом, навіть у «мовній теці»;
- кожній знахідці присвоюється confidence (0–100): високий → у списку **виділено за промовчанням**, середній → показано, але **не виділено**, низький → не показується (доступно в «розширеному» режимі).

### 5.6. Тестування движка — обов'язкове

Корпусний підхід: `tests/corpus/paths.txt` з реальними шляхами (приклади ТЗ + вивантаження реальних бібліотек) і очікуваними мітками. `cargo test` ганяє весь корпус; будь-яка зміна словника/скорингу миттєво показує регресії.

## 6. Категорії «зайвих» файлів (rules engine)

Патерни з Додатку 1 concept_mvp.txt + tikione-steam-cleaner переносяться у зовнішній `rules.json`:

```json
{ "category": "redist_file", "pattern": "^(vcredist).*\\.exe$", "desc": "MS Visual C++ Redist", "confidence": 95 }
```

Категорії: `redist_folder`, `redist_file`, `docs_folder`, `docs_file`, `bonus`, `dev_leftovers`, `localization_audio`, `localization_text`. Матчинг тек — цілими сегментами шляху; файлів — за іменем, через `RegexSet` (один прохід по всіх патернах). Обмеження: redist-патерни `.exe/.msi` застосовуються лише близько до кореня гри (redist'и лежать у корені або `_CommonRedist`-подібних теках, а не в надрах ресурсів).

## 7. Безпечне видалення

1. **За промовчанням — Кошик Windows** (крейт `trash`): звичне відновлення штатними засобами;
2. **Опційно — карантин-тека** на тому ж диску (`<бібліотека>\.gametrimmer_quarantine\<гра>\<rel_path>`): збережена структура, кнопка «Відновити» в UI, автоочистка за N днів;
3. Повне видалення — лише свідомим вибором у налаштуваннях.

Кожна операція пишеться в `operations` до виконання, статус — після. Перед операцією перевірка, що файл не заблокований.

## 8. UI (egui)

- Дерево: **Категорія → Гра → файли/теки** з чекбоксами (tri-state на групах), колонки: шлях, розмір, впевненість/правило; для великих списків — віртуалізація через `egui_extras::TableBuilder`/`show_rows`;
- підсумок «буде звільнено N ГБ» наживо;
- сканування/аналіз у фонових потоках, прогрес-бар зі скасуванням;
- темна тема egui за промовчанням (перемикач на світлу), High-DPI автоматичний;
- налаштування: мови keep-list, режим видалення, категорії, розширений режим; зберігаються в БД або `settings.json` поруч з exe;
- шрифт із кирилицею: вбудувати системний Segoe UI через `include_bytes!` або завантажити з `C:\Windows\Fonts` при старті (дефолтні шрифти egui не покривають кирилицю повністю).

## 9. Фази реалізації

### Фаза 0 — каркас проєкту (½–1 день)
- Workspace `core` + `app`, профіль релізу, clippy/rustfmt, CI-скрипт збірки;
- схема БД у `core/db`, пакетні транзакції;
- «Hello, dark egui» з кирилицею, перевірка розміру exe.

### Фаза 1 — MVP Steam end-to-end (3–5 днів)
- Порт логіки з C++: Steam через реєстр (`winreg`) + `libraryfolders.vdf`; парсинг `appmanifest_*.acf` → назви ігор;
- сканер на walkdir+rayon з індексацією в SQLite;
- rules engine з `rules.json` (категорії redist/docs/bonus/dev);
- дерево знахідок з чекбоксами, видалення в Кошик + журнал операцій.
- **Результат: уже корисна програма для Steam без мовного аналізу.**

### Фаза 2 — движок локалізацій (3–5 днів, найбільший ризик)
- Словник мов зі CLDR/ISO (назви англійською + автоніми + коди);
- токенізатор, контекстний скоринг, евристика «мовної сім'ї»;
- корпус тестів зі шляхів реальних бібліотек; ітерації до прийнятної точності;
- інтеграція в UI (категорії «Озвучка», «Тексти/субтитри» з confidence).

### Фаза 3 — мультивендорність (2–3 дні)
- Трейт `LibraryProvider` + Epic (JSON-маніфести), GOG (реєстр), Ubisoft, EA;
- ручне додавання довільної теки як «бібліотеки».

### Фаза 4 — полірування (1–2 дні)
- Карантин-режим із відновленням;
- іконка exe (`winres`), метадані версії;
- фінальна перевірка DPI 125/150/200%, портабельний zip (exe + rules.json + README);
- README, версіювання rules.json.

## 10. Головні ризики

1. **Хибні спрацювання мовного детектора** → корпусні тести + confidence + keep-list + Кошик замість видалення;
2. **Пошкодження гри видаленням «локалізації», що нею не є** → негативні маркери, «мовна сім'я» як вимога для коротких кодів, перевірка цілісності Steam як план відновлення;
3. **Продуктивність на бібліотеках у сотні тисяч файлів** → rayon-паралелізм, транзакційні пакети, інкрементальний рескан за mtime;
4. **Кирилиця/Unicode у шляхах** → у Rust шляхи — `PathBuf`/`OsStr`, без втрат кодування; у UI вбудований шрифт з кирилицею;
5. **Патерни застарівають** → зовнішній rules.json, редагований без релізу.
