## Corrections to the cards' own text

Four cards asserted things that are no longer true. All four now say so in the
appended block, but they matter for estimating:

- **GT-106** — identities are **not** hex text. They are a decimal
  `serial:index:kind:size:time:attributes` string (`safety.rs:53-63`), and always
  were. The "≈ −40 MB" saving must be recomputed against the real format before
  the work is planned. Separately, `safety-capture`'s measured 48.7 s is stale:
  commit `7ce787d` made leaf identity come from the MFT record, so the number
  needs re-measuring on the same library.
- **GT-107** — the location list is incomplete. `itch.rs:195-201` has the same
  construct, which means the "cost of the mistake" (a normal record disabling
  leftover search) is already real, not hypothetical. Xbox is structurally exempt
  and can leave the DoD.
- **GT-109** — selection profiles did **not** disappear with GT-89. They are
  live, there are three exclusion points, not two.
- **GT-105** — the reparse-point item is half done. The English message already
  names the offending nested path; the Ukrainian translation
  (`messages.rs:397-400`) throws it away, and that is the string the tooltip
  shows.

## Suggested order

1. **GT-135, then GT-74.** Both small, both close a gap a user can reach today.
   GT-74 is two halves: de-duplicate the message, and separately disable the scan
   button — `db_path` is set unconditionally at `app.rs:452` even when
   `db::open` failed, so the button is fully live against a dead database. The
   second half is not a consequence of the first.
2. **GT-107, then GT-134.** In that order. GT-107 removes the diagnostic at the
   source, which deletes the exact log line GT-134 is named after, along with the
   whole `game-entry` / `uninstall-entry` class. Whatever GT-134 has left to do
   afterwards is smaller and better defined. Steam's `GAME_ABSENT`
   (`steam.rs:101`, `:184-193`) is the pattern to copy — it already solves this
   for one provider, with tests at `steam.rs:648-699` worth using as the shape.
3. **GT-105.** The real work. Six items, deliberately independent; the card asks
   for one commit and one test each. Two notes before starting: the
   partially-deleted-directory item needs an `operations` schema change (there is
   no fingerprint column — `db.rs:67-82`), and the blocking-policy item has
   **three** copies to unify, not two (`persistence.rs:411-415`,
   `load.rs:167-177`, `ops.rs:259-268`).
4. **GT-109 — do not do this as a block.** Its items 2–5 are tests for behaviour
   GT-105 and GT-107 are already touching; writing them there is cheaper than
   coming back. What genuinely stands alone is item 6 (the Recycle Bin success
   path, today only an `#[ignore]` probe) and item 7 (the RSS/backpressure
   benchmark, AUD-09). Treat the card as a checklist to drain, not a task.
5. **GT-106.** Re-measure first, then decide. The double `tree_fingerprint`
   (`ops.rs:345-354` and `:402` both validating the same plan) is the cheap half
   and independent of the schema half. The schema half needs migration v5 — the
   slot is free, `CURRENT_SCHEMA_VERSION = 4`, `migrate_v1..v4` at
   `db.rs:213-363`.
6. **GT-108** is filler for any point. Two items are worth more than the rest:
   `.bak` files accumulating next to the exe in a portable build, and the
   rollback in `atomic_file.rs:108-124` that is entirely under `let _ =` — a
   failed rollback leaves the target with new content while the caller sees only
   the original error.
7. **GT-75** last of the active cards. Its checklist item "path normalization
   test" is mis-sized: there is no path normalizer anywhere in the tree, and
   `exe_dir()` (`worker/mod.rs:268-278`) takes the raw parent of
   `current_exe()`. Windows mutex names are case-sensitive, so the normalizer has
   to be written before the mutex means anything. The S estimate is optimistic.

**GT-42 stays blocked.** The rule is at `worker/scan.rs:1599-1638` and its
behaviour is pinned by a test at `scan.rs:3590`; moving it without concrete
examples of wrong grouping is guesswork.

## Working constraints for this epic

- **Never test against the real library.** Disposable directories, temporary
  databases, controlled fixtures only. Every card repeats this; it is the epic's
  shared boundary.
- Build after each task, test, then commit and push — in that order, straight to
  `master`. A running `gametrimmer.exe` locks `cargo build`; close it.
- Read `Scan done in` from `gametrimmer.log` after any test that scans. Over two
  minutes means a regression worth chasing before moving on.
- The analysis phase is instrumented by region only temporarily — that
  instrumentation is deliberately not committed.

## Where the numbers came from

The measurements quoted in GT-106 are from the owner's library: 1 598 games,
4 923 995 files, 720 149 findings. Wall-clock analysis phase 77.5 s against
230.5 s of thread time on six workers (×2.98). The single writer thread is busy
93 % of the phase, which is why GT-106's normalization matters for time and not
only for the 150 MB on disk. Cold-vs-warm is still open: two runs on identical
input gave 295.1 s and 77.5 s, and the standing hypothesis (NTFS metadata cache)
is testable by the first scan after a reboot.
