# GameTrimmer — Інструкції та правила проєкту

## Збірка та розміщення виконуваних файлів (Build & Distribution)
- **Розміщення збірок для користувача**: Усі готові бінарники, тестові та фінальні збірки для тестування користувачем ПОВИННІ розміщуватися виключно у теці `dist/`.
- **Заборона посилань на `target`**: Ніколи не пропонуй користувачу шукати або брати виконувані файли з `target/release/` чи `target/debug/`.
- **Скрипт повного пакування**: Для створення повноцінного портативного релізного пакета використовуй:
  ```powershell
  pwsh -File scripts/package-portable.ps1
  ```
- **Швидкі тестові збірки**: Якщо виконується компіляція для швидкої перевірки (наприклад, `cargo build --release -p gametrimmer`), скомпільований `.exe` обов'язково має бути скопійований у `dist/` (створивши теку за потреби), а користувачу надається шлях виключно до файлу в `dist/` (наприклад, `dist/gametrimmer.exe`).

## Загальні команди проєкту
- **Перевірка коду**: `cargo check --workspace`
- **Тести**: `cargo test --workspace`
- **Лінтер / Кліппі**: `cargo clippy --workspace`
- **Форматування**: `cargo fmt`

## Борд і коміти (Vikunja)
- **Коміт без оновлення картки не завершений**: після кожного коміту онови відповідну картку (чи картки) на борді GameTrimmer — допиши, що саме зроблено, і назви хеш коміту.
- **Колонка має відповідати стану**: «В роботі» тримає лише те, над чим робота ведеться зараз. Зроблене повністю → «Готово». Те, що чекає рішення власника, живої перевірки чи просто черги → назад у «До виконання» або «Беклог».
- **Опис доповнюється, а не переписується**: датований абзац у кінець, попередню історію не затирати.
- Робота з бордом — через скіл `vikunja-board` (проєкт GameTrimmer id 5, Kanban view 24).

## Перед початком будь-якої задачі
- **Спершу — сенс, потім код**: перш ніж братися за будь-яку картку, епік чи запит, поясни їхній сенс у форматі «**як працює зараз** VS **як це виглядатиме й працюватиме для користувача після впровадження**». Без винятків — навіть для техборгу й рефакторингу.
- **«Зараз» — це факти з коду, а не переказ картки**: конкретні файли й рядки, конкретна поведінка, яку користувач бачить сьогодні. Опис на борді може бути застарілим; код — ні.
- **«Після» — очима користувача**: що він побачить, натисне, отримає або перестане отримувати. Не «додамо перевірку в прифлайт», а «галочка перестане ставитися й скаже чому».
- **Невирішене — назвати невирішеним**: якщо між «зараз» і «після» лежить рішення власника (наскільки жорстко блокувати, що показувати), винести його окремим питанням, а не вирішувати мовчки.
- Тільки після цього — план і робота.
- **Тест без назви гри — не тест**: пропонуючи користувачеві перевірити щось у збірці, одразу називай конкретні ігри з його бібліотеки, на яких цей сценарій відтворюється, і чим саме вони підходять (рушій, лаунчер, тип захисту, наявність монолітів). «Гра під EAC» — не інструкція; «THE FINALS — EAC + монолітні .pak» — інструкція.
- **Називай і контрприклад**: до кожного сценарію додавай гру, на якій очікується протилежний результат, інакше зелений результат не відрізнити від «перевірка взагалі не спрацювала».
